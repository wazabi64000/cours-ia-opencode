Module 1 · Découvrir

Comprendre l'IA sans jargon

Avant d'installer quoi que ce soit, on pose les bases. En 10 minutes, tu vas comprendre ce qu'est réellement une « IA » aujourd'hui, pourquoi elle se trompe parfois, et surtout à quoi elle sert concrètement à un développeur.

🎯Objectif de ce chapitre

Comprendre ce qu'est un modèle de langage, ce qu'il sait faire, ce qu'il ne sait pas faire, et pourquoi c'est l'outil le plus utile du développeur depuis l'arrivée des IDE modernes. Aucun prérequis : aucun code à écrire ici.

Qu'est-ce qu'une IA, vraiment ?

Aujourd'hui, quand on dit « IA » dans le monde du développement, on parle presque toujours d'un grand modèle de langage (en anglais Large Language Model, ou LLM). Ce n'est ni un robot, ni un programme qui « sait » les choses comme un manuel. C'est un programme entraîné sur d'énormes quantités de texte, qui a appris à deviner le mot suivant.

🧠L'analogie du clavier de téléphone

Quand tu écris un SMS, ton téléphone te propose le mot suivant : « rendez-vous » après « prendre ». Il a appris ça en observant des millions de messages. Un LLM fait exactement la même chose, mais en beaucoup plus fort : il propose le mot suivant d'un texte, et recommence, des centaines de fois, jusqu'à produire une réponse complète.

C'est pour ça qu'on parle de prédiction et non de « réflexion ». Le modèle ne cherche pas une vérité dans une base : il génère une suite de mots qui a statistiquement du sens.

Pourquoi ça se trompe parfois ? (les hallucinations)

Comme le modèle invente la suite la plus probable, il peut inventer une information fausse avec beaucoup d'assurance : une fonction qui n'existe pas, une URL erronée, une bibliothèque obsolète. On appelle ça une hallucination.

Ce n'est pas un bug, c'est une conséquence directe de son fonctionnement. La bonne réaction n'est pas de « fuir l'IA », mais d'adopter trois réflexes :

  • Vérifier ce qui compte vraiment (code exécuté, faits, commandes).
  • Donner du contexte (le bon fichier, la bonne doc, la bonne version).
  • Faire faire à l'IA ce qu'elle fait bien : transformer, résumer, expliquer, proposer.
⚠️À retenir tout de suite

Un LLM est un assistant, pas un oracle. Il accélère énormément le travail, mais la responsabilité de ce qui part en production reste la tienne.

À quoi ça sert pour un développeur ?

Un outil comme OpenCode transforme le modèle en assistant de code qui agit dans ton projet : il lit tes fichiers, écrit du code, lance des commandes, corrige des erreurs. Concrètement, tu l'utilises pour :

🚀 Accélérer

Générer du code de départ, des tests, de la doc, des scripts d'installation.

🔍 Comprendre

Explorer un projet inconnu, poser des questions sur un fichier, résumer une architecture.

🛠️ Réparer

Coller une erreur, comprendre la cause, proposer et appliquer un correctif.

🎓 Apprendre

Se faire expliquer simplement une notion, avec des exemples adaptés à ton niveau.

Module 1 · Découvrir

Le vocabulaire : modèle, provider, agent

Six mots reviennent sans arrêt : LLM, modèle, provider, API, token, agent. Si tu les confonds, tout le reste paraît compliqué. Une fois clarifiés, la configuration d'OpenCode devient évidente.

🎯Objectif

Distinguer clairement ces concepts et savoir quel objet vit où (dans ta machine, chez un fournisseur, dans un fichier de config).

1. Le LLM (le moteur)

Le LLM est le moteur d'intelligence. Exemples : GPT, Claude, Gemini, Llama, Qwen, Gemma, Nemotron. C'est un gros fichier de « poids » entraîné sur du texte. On ne l'écrit pas à la main : on l'entraîne, ou on l'utilise tel quel.

2. Le modèle (la version précise)

Un même LLM existe en plusieurs modèles. Par exemple la famille Gemini a gemini-2.5-flash (rapide) et gemini-2.5-flash-lite (plus léger). Un modèle = un nom précis, avec sa taille, son coût, sa vitesse, sa taille de mémoire de contexte.

3. Le token (l'unité de mesure)

Un LLM ne lit pas des mots : il lit des tokens. Un token vaut grosso modo ¾ de mot en français. « Bonjour le monde » ≈ 4 tokens. Cette unité sert à deux choses : facturer (prix par million de tokens) et limiter (la fenêtre de contexte).

💰Le token, c'est le « compteur »

Pense à un taxi : on paie au kilomètre, pas à la destination. Ici, on paie par token, et la « course » a deux compteurs : les tokens d'entrée (ce que tu envoies) et les tokens de sortie (ce que le modèle répond, plus cher).

4. La fenêtre de contexte (la mémoire de travail)

Un modèle ne « se souvient » pas de la conversation précédente par magie. À chaque échange, on lui renvoie tout le texte utile (ton message + l'historique + les fichiers). La quantité maximale qu'il peut recevoir s'appelle la fenêtre de contexte (ex. : 200 000 tokens).

┌──────────────── FENÊTRE DE CONTEXTE (ex. 200 000 tokens) ────────────────┐ │ instructions │ historique conversation │ fichiers fournis │ réponse │ └──────────────────────────────────────────────────────────────────────────┘ Plus le contexte est gros → plus c'est lent et cher → d'où l'utilité de la "compaction" (chapitre 10) qui résume le vieux contexte.

5. Le provider (le fournisseur)

Un provider est l'entreprise (ou le logiciel) qui fait tourner le modèle et te le donne via une API. Tu ne possèdes pas le modèle : tu loues sa puissance de calcul. Exemples : OpenRouter, Anthropic, OpenAI, Google, Groq, Hugging Face, et en local : Ollama.

💡Provider = le robinet

Le modèle est l'eau. Le provider est le robinet qui te la donne, avec un prix et un débit (vitesse). OpenRouter va plus loin : c'est un robinet qui donne accès à des centaines de modèles au même endroit.

6. L'API (le guichet)

Une API (Application Programming Interface) est la porte d'entrée technique : une adresse web à laquelle on envoie une requête, et qui renvoie une réponse. Pour accéder à l'API d'un provider, on utilise une clé API (un mot de passe secret que tu génères sur le site du provider).

🔒Sécurité : ta clé API

Une clé API, c'est comme une carte bancaire. On ne la met jamais dans un dépôt Git public, ni en clair dans un fichier partagé. OpenCode range tes clés dans sa base locale (chapitre 05), et pour les fichiers de config on utilise la syntaxe {env:NOM_DE_VARIABLE}.

7. L'agent (le chef d'orchestre)

Un LLM seul ne fait que répondre du texte. Un agent est un LLM doté d'une mission, d'outils et de règles : il peut décider de lire un fichier, lancer une commande, écrire du code, puis recommencer. C'est ce qui transforme un « chatbot » en collaborateur qui agit.

┌──────────────────── AGENT ────────────────────┐ │ rôle (system prompt) + outils + permissions │ └────────────────────────┬──────────────────────┘ │ décide et appelle ┌────────────────────────▼──────────────────────┐ │ MODÈLE (le moteur qui rédige les décisions) │ └────────────────────────┬──────────────────────┘ │ utilise OUTILS : lire fichier · éditer · terminal · web · MCP

Module 2 · Installer

Installer OpenCode (toutes les méthodes)

OpenCode est un agent de code en ligne de commande, gratuit et open source. Il existe une méthode d'installation pour chaque système. On va choisir la tienne, l'installer, puis vérifier que tout fonctionne.

🎯Objectif

Avoir la commande opencode qui répond dans ton terminal, quelle que soit ta machine.

⛵️Tu es sur quoi ?

Choisis ta section : Linux / macOS (la plus simple), ou Windows. Tu peux tester ton système avec uname -a (Linux/macOS).

Méthode 1 — L'installeur officiel (recommandé)

Une seule ligne, qui télécharge le binaire adapté à ta machine. C'est la méthode la plus fiable.

curl -fsSL https://opencode.ai/v2/install | bash

Ce que fait cette commande, décomposé :

  • curl télécharge un script d'installation.
  • -fsSL = échouer silencieusement, suivre les redirections, mode silencieux.
  • | bash exécute ce script, qui place le binaire opencode sur ton système.
⚠️Réflexe de sécurité

Exécuter un script téléchargé demande de la confiance. La règle : télécharge depuis le site officiel opencode.ai, jamais depuis un lien trouvé au hasard. Si tu préfères un paquet géré, utilise la méthode 2.

Méthode 2 — Par gestionnaire de paquets

Utile si tu as déjà Homebrew, npm, bun, pnpm ou yay/paru : la mise à jour est alors automatique.

Homebrew (macOS / Linux)

brew install anomalyco/tap/opencode-v2

npm / Node.js

npm install -g @opencode/cli

bun

bun install -g --trust @opencode/cli

pnpm

pnpm add -g --allow-build=@opencode/cli @opencode/cli

yarn

yarn global add @opencode/cli

Arch AUR (Linux — version beta)

paru -S opencode-beta
⚠️Note importante (2026)

Les gestionnaires de paquets Windows ne sont pas supportés par OpenCode. Sur Windows, utilise la méthode 3 (binaire téléchargeable) ou installe d'abord WSL.

Méthode 3 — Binaire autonome (Windows, ou sans gestionnaire)

Télécharge l'archive correspondant exactement à ton système, décompresse-la, puis place le binaire dans un dossier présent dans ton PATH.

Méthode 4 — Docker, Desktop et Web

Trois autres façons d'utiliser OpenCode, sans passer par le terminal :

🐳 Docker

ghcr.io/anomalyco/opencode:2.0.0 — pour exécuter OpenCode dans un conteneur.

💻 Desktop

Application native (macOS, Windows, Linux). Pratique si le terminal te rebute au début.

🌐 Web

opencode pair ouvre une interface web locale avec URL et mot de passe.

Vérifier l'installation

opencode --version
# → opencode v2.x.x

Si une version s'affiche, c'est bon. Tu verras aussi la version des outils internes : OpenCode embarque sa propre logique, tu n'as rien d'autre à installer pour commencer.

🚨Erreur fréquente : « command not found »

Elle signifie simplement que le dossier contenant opencode n'est pas dans ton PATH. Deux solutions :

  • Pour npm : vérifie que npm bin -g (ou npm prefix -g) est bien dans ton PATH.
  • Pour le binaire : déplace-le dans /usr/local/bin (Linux/macOS) comme montré plus haut.

Désinstaller proprement

Pour tout enlever, sans toucher à tes données de session ni à ta configuration :

# 1. Prévisualiser ce qui sera supprimé
opencode uninstall --dry-run

# 2. Confirmer la suppression
opencode uninstall
💡Bon à savoir

La désinstallation retire le cache global et arrête les services, mais conserve tes sessions, ta configuration et tes clés. Tu pourras réinstaller sans rien reconfigurer.

🔧À faire maintenant
  1. Choisis ta méthode (méthode 1 pour la plupart des gens) et exécute la commande.
  2. Vérifie avec opencode --version.
  3. Lance opencode --help et note les sous-commandes que tu reconnais déjà : run, mini, mcp, auth, plugin, service.
  4. En cas de blocage, relis l'encadré « command not found » ci-dessus.
✅À retenir
  • La méthode la plus simple : curl -fsSL https://opencode.ai/v2/install | bash.
  • Sinon : gestionnaire de paquets, ou binaire téléchargeable (obligatoire sur Windows natif).
  • On vérifie toujours avec opencode --version.
  • La désinstallation ne supprime ni ta configuration ni tes sessions.
Module 2 · Installer

Premier lancement & l'interface

OpenCode se lance dans un dossier de projet. Il ouvre une interface plein écran (le TUI) et te laisse discuter avec l'IA. Voici tout ce qu'il faut savoir pour ne pas être perdu au premier lancement.

🎯Objectif

Lancer OpenCode, comprendre l'écran, et connaître les 6 commandes essentielles (/connect, /models, /help…).

Lancer OpenCode

Place-toi d'abord dans le dossier du projet sur lequel tu veux travailler, puis lance OpenCode :

cd ~/mes-projets/mon-app
opencode

Tu peux aussi viser un dossier en une fois :

opencode ~/mes-projets/mon-app
📁Pourquoi le dossier compte

OpenCode lit les fichiers du dossier dans lequel tu le lances. Lancer OpenCode dans ~/mon-app, c'est lui dire : « voici le projet dont je te parle ». C'est ce qui lui permet de lire et modifier le bon code.

Exemple d'utilisation « automatisée » :

Premier vrai pas : connecter un provider

Sans provider connecté, OpenCode n'a aucun modèle à utiliser. Au premier lancement, tape :

/connect

Une liste de providers apparaît. Choisis-en un, suis les étapes (coller une clé API ou te connecter en OAuth), puis vérifie avec :

/models

Tu dois voir des modèles. On détaille les providers et les modèles gratuits au prochain module.

Le service en arrière-plan

OpenCode fonctionne en client/serveur : l'interface discute avec un service qui gère les sessions, la config et les outils. En général on ne s'en occupe pas… sauf s'il faut le redémarrer :

opencode service status     # Voir l'état
opencode service restart    # Redémarrer le service
opencode api get /api/info  # Vérifier que l'API répond

  • Trois modes : opencode (TUI), run (script), mini (léger).

Module 3 · Providers & modèles

Qu'est-ce qu'un provider ?

Un provider, c'est le fournisseur qui met un modèle à ta disposition via Internet. Tu en relies un à OpenCode avec /connect, et c'est parti. Mais comprendre ce qui se passe derrière te fera économiser beaucoup de temps et d'argent.

🎯Objectif

Savoir connecter un provider, où sont stockées tes clés, et comment brancher un fournisseur sur mesure.

Connecter un provider

/connect

Méthode terminal : auth login

# Picker interactif de providers

# Voir les comptes connectés
opencode auth list

Où sont mes clés ? (et pourquoi c'est sûr)

Les clés et jetons OAuth sont stockés dans la base SQLite locale d'OpenCode, pas dans un fichier texte en clair. Tu peux afficher l'emplacement :

opencode debug paths db
# → ~/.local/share/opencode/opencode.db (chemin habituel)
🔒Ne fais JAMAIS ça

Ne copie-colle pas ta clé API dans un fichier versionné par Git, ni dans un message public. Si tu dois l'utiliser dans un fichier de configuration, on verra au chapitre 08 la forme sécurisée : {env:NOM_DE_VARIABLE}.

Le cas particulier des variables d'environnement

Au lieu de saisir une clé dans OpenCode, tu peux la fournir via une variable d'environnement. Idéal pour les serveurs et l'automatisation :

# Pour un lancement ponctuel en mode privé
ANTHROPIC_API_KEY=sk-ant-... opencode --standalone

# Pour le service d'arrière-plan partagé
opencode service set env ANTHROPIC_API_KEY sk-ant-...
opencode auth list

Ces connexions par environnement n'apparaissent pas comme des « comptes » : pour les enlever, on désactive la variable avec opencode service unset env ….

Combien de providers connecter ?

  • Pour débuter : un seul suffit (OpenRouter, gratuit et polyvalent).
  • Pour la résilience : deux ou trois. Si l'un tombe en rate limit, on change de modèle avec /models (et on automatise ce basculement au chapitre 10).

🔄Les listes bougent : la règle d'or

Un modèle gratuit aujourd'hui peut disparaître demain. Ne mémorise pas les noms : mémorise où regarder. Les sections ci-dessous t'apprennent à filtrer le catalogue en quelques secondes.

OpenRouter : la source n°1 de modèles gratuits

OpenRouter agrège des centaines de modèles derrière une seule clé API. Les modèles gratuits ont un identifiant qui finit par :free (ex. : google/gemma-4-31b-it:free).

Comment les trouver, en pratique

  1. Va sur openrouter.ai/models et filtre sur les modèles gratuits.

Module 3 · Providers & modèles

Choisir son modèle (gratuit ou payant)

Il existe des centaines de modèles. Bonne nouvelle : pour choisir, tu n'as besoin que de cinq critères. Et le meilleur modèle n'est presque jamais le plus « intelligent » : c'est celui qui répond au bon besoin au bon prix.

🎯Objectif

Savoir comparer deux modèles en 30 secondes, et décider gratuit ou payant selon l'usage.

Les 5 critères qui comptent

1. Le contexte

Combien de tokens il peut « tenir » en mémoire. 32k suffit pour un fichier ; 200k+ pour un gros projet.

2. Les outils (tool calling)

Indispensable pour un agent : le modèle doit savoir « appeler » lire/écrire/terminal. Sans ça, pas d'action.

3. Le prix

En général exprimé en dollars par million de tokens, séparément entrée et sortie.

4. La qualité sur le code

Un modèle excellent en rédaction peut être moyen en code. Cherche un modèle « coder ».

5. La vitesse (latence)

Débit en tokens/seconde. Crucial si tu utilises l'IA en continu.

Bonus : le multimodal

Accepte-t-il des images (captures d'écran, maquettes) ? Utile pour le front.

🚗Une voiture pour chaque trajet

Prendre un modèle payant pour renommer une variable, c'est comme louer un camion pour acheter du pain. L'astuce des pros : un « petit » modèle pas cher pour les tâches simples, un « gros » modèle seulement quand c'est justifié.

Gratuit ou payant ? La règle simple

SituationChoix conseillé
Apprendre, tester, s'entraînerGratuit
Petites tâches répétitives (résumé, formatage, commit)Gratuit ou modèle très bon marché
Refactoring de plusieurs fichiersModèle payant « coder » de milieu de gamme
Architecture complexe, bug coriaceLe meilleur modèle disponible, ponctuellement
Données sensibles / hors ligneLocal (Ollama)

Comprendre le prix (sans se ruiner)

Les modèles se facturent par million de tokens. Les tokens de sortie coûtent généralement 3 à 5 fois plus cher que ceux d'entrée. Exemple de calcul mental :

Un fichier de 200 lignes ≈ 3 000 tokens d'entrée Le modèle répond 500 lignes ≈ 6 000 tokens de sortie À 1 $/M en entrée et 4 $/M en sortie : entrée : 3 000 × 1/1 000 000 = 0,003 $ sortie : 6 000 × 4/1 000 000 = 0,024 $ ─────────── total ≈ 0,027 $ (≈ 2,5 centimes) → Un échange "normal" coûte quelques centimes. Ce qui coûte cher, c'est de renvoyer TOUT le projet à chaque fois.
💡Les 3 $ qui font la différence

Les modèles premium coûtent souvent 5 à 30 $ par million de tokens ; les modèles coder économiques (DeepSeek, Qwen, certains open source) tournent autour de quelques dizaines de centimes pour des résultats très proches sur le code.

Identifier un bon modèle sur models.dev

Pour chaque modèle, tu y trouves : la fenêtre de contexte, le prix entrée/sortie, le support des outils et des images, et les variants (niveaux de raisonnement). Trois réflexes :

  • Vérifie d'abord que les outils sont supportés (sinon aucun agent ne marchera).
  • Regarde le prix de sortie, c'est lui qui domine la facture.
  • Préfère un contexte suffisant plutôt que maximal : un très gros contexte coûte cher à remplir.

Les variants : plus ou moins de raisonnement

Beaucoup de modèles exposent des variants (#high, #low…) qui règlent l'effort de raisonnement. On les choisit au moment de l'exécution :

opencode run --model openai/gpt-5.2#high "Analyse cette architecture"
opencode run --model openai/gpt-5.2#low  "Reformate ce JSON"

Règle : #low pour le mécanique, #high pour le difficile. On économise du temps et de l'argent.

🔧À faire maintenant
  1. Dans /models, choisis deux modèles : un gratuit et un payant (même le moins cher).
  2. Pose exactement la même question aux deux : opencode run --model … "Écris une fonction JS qui vérifie si un email est valide".
  3. Compare : qualité de la réponse, vitesse, et (si affiché) le coût.
  4. Note ton verdict. Tu viens de créer ta grille de choix personnelle.
✅À retenir

  • Outils = obligatoire pour un agent ; sans tool calling, rien ne fonctionne.
  • On paie par million de tokens, la sortie coûte plus cher que l'entrée.
  • Un petit modèle pour le simple, un gros seulement quand c'est utile. Les variants aident.

Configurer ses providers (fichier de config)

Jusqu'ici on a tout fait à la souris. Maintenant on écrit le petit fichier qui rend ta configuration reproductible : modèle par défaut, providers, modèles sur mesure, variables d'environnement. C'est la pièce qui fait passer de « bricolage » à « poste de travail ».

🎯Objectif

Écrire un opencode.jsonc propre (version V2) avec au moins un provider, un modèle par défaut et un provider personnalisé, sans jamais exposer de secret.

Où se trouve ce fichier ?

PortéeEmplacement
Tous mes projets~/.config/opencode/opencode.json(c)
Un seul projet<projet>/opencode.json(c)
Un seul projet (variante)<projet>/.opencode/opencode.json(c)

OpenCode fusionne les fichiers du plus lointain au plus proche : le projet écrase le global, sans effacer ce qui n'entre pas en conflit.

⚠️Version 1 ou Version 2 ?

OpenCode 2 (V2) utilise des noms au pluriel : providers, agents, plugins, permissions. Les anciens fichiers V1 (singulier provider, agent…) restent acceptés, mais on écrit la forme V2 dans ce cours. Si tu veux convertir un vieux fichier, demande simplement à OpenCode : Migre ma configuration OpenCode de V1 vers la forme V2.

Un fichier minimal

{
  "$schema": "https://opencode.ai/config.json",
  "model": "openrouter/anthropic/claude-sonnet-4"
}

Le champ $schema active l'autocomplétion dans ton éditeur. Le champ model choisit le modèle par défaut, au format provider/modèle.

Un fichier complet, commenté

{
  "$schema": "https://opencode.ai/config.json",

  // Modèle utilisé par défaut dans les sessions
  "model": "openrouter/qwen/qwen3.8-27b:free",

  // Agent principal par défaut (voir chapitre 11)
  "default_agent": "build",

  // Le "petit" modèle (titres, résumés) → un modèle rapide et pas cher
  "agents": {
    "title": { "model": "openrouter/google/gemma-4-31b-it:free" }
  },

  "providers": {
    "openrouter": {
      "env": ["OPENROUTER_API_KEY"],
      "models": {
        "qwen/qwen3.8-27b:free": { "name": "Qwen 3.8 (gratuit)" }
      }
    },

    // Provider personnalisé compatible OpenAI
    "mon-serveur": {
      "name": "Mon serveur local",
      "package": "@opencode/ai/providers/openai-compatible",
      "settings": {
        "baseURL": "http://127.0.0.1:8000/v1",
        "apiKey": "{env:MON_SERVEUR_KEY}"
      },
      "models": {
        "coder": {
          "modelID": "model-name-on-server",
          "name": "Mon codeur",
          "capabilities": { "tools": true, "input": ["text"], "output": ["text"] },
          "limit": { "context": 32768, "output": 8192 }
        }
      }
    }
  }
}

Décomposons les blocs importants :

  • env : la liste des variables d'environnement qui peuvent fournir la clé.
  • package : le « moteur » qui parle au provider. Pour une API compatible OpenAI, on utilise @opencode/ai/providers/openai-compatible.
  • settings.baseURL : l'adresse de l'API.
  • settings.apiKey : jamais en clair ! On écrit {env:NOM}, la valeur vient de ton environnement.
  • models : les modèles exposés, avec leur modelID réel, leurs capacités et leurs limites.
🔒La règle d'or des secrets

Dans un fichier de config versionné, on n'écrit jamais une clé en clair. On utilise {env:NOM_DE_VARIABLE} et on définit la variable dans le système. Comme ça, le fichier peut être partagé sans risque.

export OPENROUTER_API_KEY="sk-or-..."
export MON_SERVEUR_KEY="ma-cle-locale"

Rediriger un provider existant

Tu peux faire passer un provider du catalogue par un proxy compatible en changeant juste l'URL :

{
  "providers": {
    "anthropic": {
      "settings": { "baseURL": "https://mon-proxy.example.com/anthropic" }
    }
  }
}

Variants et coûts d'un modèle

On peut définir ses propres variants (niveaux de raisonnement) et déclarer les prix pour que la facturation affichée soit juste :

{
  "providers": {
    "openai": {
      "models": {
        "gpt-5.2": {
          "variants": [
            { "id": "fast", "settings": { "reasoningEffort": "low" } },
            { "id": "deep", "settings": { "reasoningEffort": "high" } }
          ],
          "cost": { "input": 1.25, "output": 10 },
          "limit": { "context": 200000, "output": 32000 }
        }
      }
    }
  }
}

Réduire les coûts (et rester efficace)

Beaucoup pensent que l'IA coûte cher. En réalité, mal configurée, elle coûte cher ; bien configurée, elle coûte des centimes. Voici les leviers concrets, du plus efficace au plus fin.

🎯Objectif

Diviser ta facture (parfois jusqu'à zéro) sans perdre en qualité, grâce à sept techniques.

Levier 1 — Un petit modèle pour les petites tâches

Les tâches mécaniques (titre de session, résumés, formatage) n'ont pas besoin d'un modèle premium. On configure l'agent title sur un modèle gratuit ou très bon marché :

{
  "agents": {
    "title": { "model": "openrouter/google/gemma-4-31b-it:free" }
  }
}

Levier 2 — Le bon variant au bon moment

Le variant règle l'effort de raisonnement. Un variant bas consomme moins de tokens de réflexion :

opencode run --model openai/gpt-5.2#low "Reformate ce tableau"

Levier 3 — Réduire le contexte (le plus gros levier)

Le coût explose quand on renvoie tout le projet à chaque message. Trois réflexes :

  • Utiliser @fichier pour cibler un seul fichier, pas tout le dossier.
  • Demander un diff (les lignes qui changent) plutôt qu'une réécriture complète.
  • Démarrer une nouvelle session quand le sujet change : l'ancien historique ne suit pas.

Levier 4 — La compaction automatique

Quand une session devient longue, OpenCode peut résumer le vieux contexte pour ne pas le renvoyer en entier. On règle le budget conservé :

{
  "compaction": {
    "auto": true,
    "keep": { "tokens": 8000 },
    "buffer": 20000
  }
}
  • auto : active la compaction automatique.
  • keep.tokens : combien de contexte récent on garde tel quel.
  • buffer : marge de sécurité avant débordement.

Levier 5 — Limiter ce que l'agent peut faire

Un agent qui ne peut pas lancer de commandes inutiles consomme moins. On utilise les permissions (on les approfondit au chapitre 11) et la limite d'étapes :

{
  "agents": {
    "economique": {
      "mode": "primary",
      "steps": 6,
      "permissions": [
        { "action": "shell", "resource": "*", "effect": "deny" },
        { "action": "webfetch", "resource": "*", "effect": "deny" }
      ]
    }
  }
}

Levier 6 — Les tokens en cache

Chez beaucoup de providers, relire un préfixe stable (les mêmes instructions au début) coûte bien moins cher grâce au cache. Concrètement : garde tes instructions stables et groupe-les au début du contexte, ne les réécris pas à chaque message.

# OpenRouter renvoie le détail des tokens en cache dans la réponse :
# usage.prompt_tokens_details.cached_tokens

Levier 7 — Le basculement automatique (fallback)

Quand un provider atteint son quota, on veut basculer sans être bloqué. Deux approches :

A. Côté provider (le plus simple)

OpenRouter sait enchaîner plusieurs modèles en cas d'échec, via une liste de secours passée dans le corps de la requête.

B. Côté OpenCode (le plus souple)

Un plugin peut observer les erreurs de session et changer de modèle tout seul. On voit les plugins au chapitre 15.

Exemple d'approche A : déclarer un modèle de secours dans le corps de la requête du provider :

{
  "providers": {
    "openrouter": {
      "body": {
        "models": [
          "qwen/qwen3.8-27b:free",
          "google/gemma-4-31b-it:free",
          "openrouter/free"
        ],
        "route": "fallback"
      }
    }
  }
}
⚠️Les options de corps sont spécifiques au provider

Qu'est-ce qu'un agent ?

Jusqu'ici, tu as parlé à un modèle. Un agent va plus loin : il a un rôle, des outils, des règles, et parfois même des agents assistants. C'est la brique qui fait vraiment gagner du temps.

🎯Objectif

Comprendre les trois modes d'agent, connaître les agents intégrés à OpenCode, et savoir à quoi sert une permission.

La recette d'un agent

AGENT = rôle (system prompt) + modèle + outils + permissions + limites Exemples de rôles : - "build" : le développeur par défaut - "plan" : réfléchit sans modifier les fichiers - "reviewer": relit le code, ne l'édite jamais

Retiens la formule : un agent = un LLM spécialisé pour une mission, avec des garde-fous. Le même modèle peut donc servir dans plusieurs agents très différents.

Les trois modes

ModeOù il vitPour quoi
primaryLa session principale (toi à lui)Ton agent de travail principal
subagentDans une session enfant, lancé par un autre agentUne tâche déléguée (revue, recherche)
allLes deuxUsage souple
👥Une équipe

L'agent primary est le collègue à qui tu parles tous les jours. Les subagents sont des spécialistes qu'il appelle au besoin : le relecteur, l'explorateur de code. Tu ne discutes pas avec eux : ils travaillent en coulisses et rendent leur rapport.

Les agents intégrés à OpenCode

AgentModeCe qu'il fait
buildprimaryL'agent de code par défaut. Peut lire et éditer ; les actions sensibles demandent une confirmation.
planprimaryExplore et planifie sans modifier les fichiers normaux. Idéal pour réfléchir avant d'agir.
generalsubagentRecherche et tâches multi-étapes, avec de larges accès aux outils.
exploresubagentCherche et lit le code ou le web, sans rien modifier. Parfait pour comprendre un projet inconnu.

Il existe aussi des agents cachés (compaction, title, summary) que tu ne choisis pas directement : ils font la maintenance (titrer les sessions, résumer le contexte).

Le bon réflexe : plan avant build

# 1. Demander un plan (l'agent explore sans rien casser)
/plan Comment ajouter une authentification à ce projet ?

# 2. Revenir en build et exécuter
/build Applique le plan étape par étape.

Planifier coûte moins cher que réparer. On explore, on valide l'approche, puis on exécute.

Les permissions : le contrôle

Une permission dit ce qu'un agent a le droit de faire. En V2, c'est une liste ordonnée de règles : la dernière règle qui correspond gagne.

{
  "permissions": [
    { "action": "shell", "resource": "git push *", "effect": "ask" },
    { "action": "*",     "resource": "*",           "effect": "allow" }
  ]
}
ChampSignification
actionL'outil concerné (voir tableau ci-dessous). Les jokers * sont permis.
resourceCe qui est visé (chemin, commande, identifiant d'agent).
effectallow, ask (demande), ou deny.
ActionCouvre
shellLes commandes terminal
editModifier/écrire des fichiers
read, glob, grepLire et chercher dans les fichiers
webfetch, websearchAccès web
subagentLancer un agent enfant
skillCharger une compétence (chapitre 14)
💡Le principe du moindre privilège

Donne à chaque agent le minimum d'accès nécessaire. Un agent de revue qui ne peut pas écrire ni lancer de commandes est à la fois plus sûr et moins coûteux.

🔧À faire maintenant
  1. Dans OpenCode, alterne entre /plan et /build sur une même demande et observe la différence.
  2. Demande à l'agent build : « Utilise le subagent explore pour me résumer l'architecture de ce dossier. »
  3. Ouvre ~/.config/opencode/opencode.json et repère les permissions globales si tu en as.
✅À retenir
  • Un agent = rôle + modèle + outils + permissions + limites.
  • Trois modes : primary, subagent, all.
  • Intégrés : build, plan, general, explore.
  • Les permissions limitent chaque agent : dernier règle gagnante.

Créer un agent local (pas à pas)

Un agent, c'est juste un fichier texte dans un dossier. On va en créer un vrai, du nom à la permission, puis l'utiliser.

🎯Objectif

Créer un agent de revue de code en lecture seule, le déclarer comme agent principal par défaut, et le tester.

Où placer le fichier ?

PortéeEmplacement
Global (tous les projets)~/.config/opencode/agents/<nom>.md
Projet<projet>/.opencode/agents/<nom>.md

Le chemin devient l'identifiant. Exemple : .opencode/agents/team/reviewer.md → identifiant team/reviewer.

Pas à pas

  1. Créer le dossier.
mkdir -p ~/.config/opencode/agents
  1. Écrire le fichier de l'agent. Le corps du Markdown devient le « system prompt » (les instructions données au modèle).
---
description: Relit les changements et signale les bugs sans jamais modifier le code
mode: subagent
model: openrouter/qwen/qwen3.8-27b:free
permissions:
  - action: edit
    resource: "*"
    effect: deny
  - action: shell
    resource: "*"
    effect: deny
---

Tu es un relecteur de code strict et bienveillant.

Ta mission :
- Lire les changements (diff) fournis.
- Lister les problèmes par ordre de gravité : bug, faille, test manquant.
- Pour chaque problème : le fichier, la ligne, et pourquoi c'est un problème.

Règles :
- Tu ne modifies JAMAIS les fichiers.
- Tu ne lances AUCUNE commande.
- Tu réponds en français, en phrases courtes.

Décomposons le frontmatter (entre les ---) :

ChampRôle
descriptionCe que l'agent fait. Essentiel pour les subagents : c'est ce que le modèle lit pour choisir de le lancer.
modeprimary, subagent ou all.
modelModèle au format provider/modèle, avec un variant optionnel après #.
permissionsLa liste ordonnée de règles vue au chapitre 11.
  1. Utiliser l'agent. Comme il est subagent, on le lance depuis l'agent principal :
Utilise le subagent reviewer pour relire mes changements actuels.

Faire de l'agent le principal (default_agent)

Pour qu'il démarre par défaut, on le déclare primary et on le nomme comme agent par défaut :

{
  "default_agent": "reviewer"
}
⚠️Attention

L'agent par défaut doit exister, être visible et supporter le mode principal. Sinon OpenCode retombe sur build.

La variante JSON (même agent, dans la config)

On peut tout définir dans opencode.jsonc sous agents :

{
  "agents": {
    "explicateur": {
      "description": "Explique le code sans jamais le modifier",
      "mode": "subagent",
      "system": "Explique le code demandé avec des exemples courts. N'édite aucun fichier.",
      "permissions": [
        { "action": "edit", "resource": "*", "effect": "deny" }
      ]
    }
  }
}
💡Fichier ou JSON ?

Les fichiers Markdown sont plus confortables pour écrire un long prompt (le corps du fichier). Le JSON est pratique pour de petits agents ou pour tout regrouper. Choisis selon ton confort ; les deux se mélangent.

Trois idées d'agents à recopier

📝 Rédacteur de doc

Lit le code et produit un README clair. Accès : lecture seule + écriture limitée aux *.md.

🧪 Testeur

Génère des tests pour un fichier donné. Accès : lecture + écriture dans tests/.

🔎 Explorateur

Résume l'architecture d'un dossier. Accès : lecture seule, mode subagent.

🚨Erreur fréquente

Un frontmatter mal indenté (YAML sensible aux espaces) empêche l'agent de se charger. Si ton agent n'apparaît pas : vérifie l'orthographe de permissions, l'indentation, et que le fichier finit bien par .md.

🔧À faire maintenant
  1. Crée ~/.config/opencode/agents/reviewer.md avec le contenu ci-dessus.
  2. Relance OpenCode (ou redémarre le service : opencode service restart).
  3. Demande à l'agent principal d'utiliser reviewer sur un fichier modifié.
  4. Vérifie qu'il refuse bien d'éditer : demande-lui de corriger un bug… il doit répondre qu'il ne modifie pas.
✅À retenir
  • Un agent = un fichier .md dans ~/.config/opencode/agents/ ou .opencode/agents/.
  • Le frontmatter définit description, mode, model, permissions ; le corps Markdown devient le prompt système.
  • default_agent choisit l'agent de départ.
  • Même agent définissable en JSON sous agents.

Les Skills : des compétences réutilisables

Tu répètes souvent les mêmes consignes à l'agent ? Une skill (compétence) est une fiche de consignes rangée à part, qu'OpenCode va chercher tout seul quand le sujet s'y prête. Tes prompts restent courts, tes consignes ne se perdent plus.

🎯Objectif

Savoir ce qu'est une skill, où la ranger, comment la rendre découvrable — et en créer une de bout en bout.

Le problème qu'elles résolvent

Sans skill, tu réécris les mêmes consignes ou tu les entasses dans le prompt système. Résultat : un prompt énorme, chargé à chaque message, même quand ce n'est pas utile.

🍲Une recette de cuisine

Tu n'apprends pas par cœur toutes tes recettes. Tu les ranges dans un classeur et tu sors la bonne fiche au moment de cuisiner. Une skill, c'est ça : une fiche de consignes rangée à part. Un modèle lit cette fiche uniquement quand il en a besoin, ce qui économise du contexte (et de l'argent).

Anatomie d'une skill

Une skill, c'est un dossier avec un fichier SKILL.md, entouré de ses fichiers utiles (scripts, modèles, références).

.opencode/skills/
└── git-release/
    ├── SKILL.md
    ├── scripts/
    │   └── changelog.ts
    └── references/
        └── release-policy.md

Dans SKILL.md, on décrit quand utiliser la skill, puis comment procéder. Les chemins écrits à l'intérieur sont relatifs au dossier contenant SKILL.md : la skill reste autonome, où qu'on la copie.

Un exemple complet

---
name: Release
description: Préparer une release (notes, version, tag)
---

## Marche à suivre
1. Lis references/release-policy.md.
2. Résume les changements mergés depuis le dernier tag.
3. Propose le numéro de version AVANT de modifier le moindre fichier.
4. Lance scripts/changelog.ts seulement après validation.

Le frontmatter (entre les ---) sert à nommer la skill et à dire au modèle quand elle est pertinente. Le corps Markdown, lui, devient les instructions chargées le moment venu.

Champ du frontmatterRôle
nameNom affiché. Par défaut, c'est l'identifiant tiré du chemin.
descriptionLe texte qui permet au modèle de découvrir la skill. Sans description, elle n'est pas proposée automatiquement.
metadata.opencode/autoinvokeMis à false, la skill reste disponible mais n'est plus suggérée au modèle.
disable-model-invocationtrue : même effet que ci-dessus.

Où OpenCode les cherche (automatiquement)

PortéeEmplacements
Global~/.config/opencode/skills
Global (compatibilité)~/.claude/skills, ~/.agents/skills
Projet.opencode/skills
Projet (compatibilité).claude/skills, .agents/skills

Deux formes de fichier sont acceptées : un simple .md à la racine de la source (ex. skills/review.md), ou un dossier contenant un fichier nommé exactement SKILL.md.

L'identifiant (ID), une règle à retenir

C'est le chemin du fichier qui définit l'ID, pas le name du frontmatter. L'ID est sensible à la casse.

FichierID
<source>/git-release.mdgit-release
<source>/git-release/SKILL.mdgit-release
<source>/release/SKILL.mdrelease
⚠️Le piège classique

Une skill rangée dans .opencode/skills/release/SKILL.md a l'ID release, même si son name vaut « Git Release ». Pour l'appeler à la main, c'est @release — pas @Git Release.

Qui gagne en cas de doublon ?

Si deux sources définissent le même ID, c'est la source enregistrée en dernier qui l'emporte. En pratique, un fichier de projet écrase le fichier global du même nom :

~/.config/opencode/skills/git-release/SKILL.md   ← priorité basse
.opencode/skills/git-release/SKILL.md            ← chargée

Ajouter d'autres sources (locales ou HTTP)

Pour partager des skills d'équipe, on déclare des dossiers ou des catalogues HTTP dans le tableau skills :

{
  "$schema": "https://opencode.ai/config.json",
  "skills": [
    "./team-skills",
    "~/shared/opencode-skills",
    "https://exemple.com/opencode/skills/"
  ]
}

Un chemin relatif part du dossier de travail, pas du fichier de config. Une URL charge un catalogue : un index.json qui liste les skills disponibles. Les tableaux skills de tous les fichiers de config se cumulent.

Contrôler qui peut charger quoi

Comme pour les autres outils, on utilise une permission. C'est l'ID de la skill qui sert de ressource :

{
  "permissions": [
    { "action": "skill", "resource": "*",           "effect": "allow" },
    { "action": "skill", "resource": "internal-*",  "effect": "deny" },
    { "action": "skill", "resource": "experimental-*", "effect": "ask" }
  ]
}

La dernière règle qui correspond gagne. deny masque même la skill au modèle ; ask demande ton accord avant de la charger.

🔧À faire maintenant
  1. Crée le dossier .opencode/skills/mes-conventions/ dans un projet.
  2. Ajoute un fichier SKILL.md avec un name, une description, et 3 règles de ton équipe (indentation, tests, nommage).
  3. Relance OpenCode, puis demande quelque chose qui touche au sujet de la skill : elle doit être proposée.
  4. Appelle-la explicitement avec @mes-conventions et vérifie qu'elle se charge.
✅À retenir
  • Une skill = un dossier avec SKILL.md (ou un .md racine).
  • La description sert à la découvrir automatiquement.
  • L'ID vient du chemin, pas du name ; il est sensible à la casse.
  • Chargement à la demande : @id, ou via l'outil skill.
  • Permission skill pour autoriser, demander ou bloquer.

Les plugins : brancher des outils

Un plugin ajoute des outils, des hooks et des intégrations à OpenCode. C'est la manière la plus puissante d'étendre l'assistant : on branche un paquet npm ou un petit fichier TypeScript, et OpenCode gagne une nouvelle capacité.

🎯Objectif

Comprendre à quoi sert un plugin, savoir en installer un avec la CLI, et connaître les dossiers de découverte automatique.

Plugin ou skill ?

SkillPlugin
C'est…Des consignes (du texte)Du code qui ajoute des capacités
Ça sert à…Guider l'agent sur une méthodeAjouter un outil, un hook, une intégration
DifficultéFacile (Markdown)Moyenne à avancée (TypeScript)
🔌La prise multiple

La skill explique comment faire les choses. Le plugin branche un nouvel appareil sur la prise : une connexion à un service, une commande spéciale, un événement déclenché au bon moment. On installe d'abord, on code ensuite — et seulement si le besoin existe.

Installer un plugin avec la CLI

Le plus simple : on ajoute un paquet publié sur npm. OpenCode l'installe et l'enregistre pour toi.

# Ajouter un plugin (avec ou sans version / tag)
opencode plugin add opencode-acme-plugin
opencode plugin add opencode-acme-plugin@1.2.0
opencode plugin add @acme/opencode-plugin@latest

# Voir, vérifier, mettre à jour, retirer
opencode plugin list
opencode plugin list --builtin
opencode plugin check
opencode plugin update
opencode plugin remove opencode-acme-plugin@1.2.0

Les dépôts Git sont aussi acceptés (branches, tags, commits complets), y compris privés via tes identifiants Git.

Ce que la CLI écrit dans la config

Un plugin ajouté finit dans le tableau plugins. Tu peux aussi l'y mettre à la main, avec des options :

{
  "$schema": "https://opencode.ai/config.json",
  "plugins": [
    "opencode-acme-plugin@1.2.0",
    "./plugins/local",
    {
      "package": "@acme/opencode-plugin",
      "options": { "agent": "reviewer", "strict": true }
    }
  ]
}

Les chemins relatifs se résorbent depuis le fichier de config qui les contient. Les tableaux de plusieurs fichiers se cumulent, du moins prioritaire au plus prioritaire.

Découverte automatique

Aucune config n'est nécessaire pour un plugin posé dans un dossier .opencode/plugins/ : OpenCode charge directement les fichiers .ts/.js et les dossiers de paquets.

.opencode/
└── plugins/
    ├── concise.ts
    ├── reviewer.js
    └── acme-package/

Les plugins globaux suivent le même schéma sous ~/.config/opencode/plugins/.

⚠️Un piège de découverte

Un dossier plugins/ posé à côté d'un opencode.json à la racine du projet n'est pas détecté tout seul. Déplace-le sous .opencode/, ou déclare-le explicitement dans plugins.

Activer, désactiver, ordonner

Les entrées sont traitées dans l'ordre. Un - désactive, * vise tout le monde, et .* matche un préfixe d'ID. Un ID cité plus tard réactive un plugin.

{
  "plugins": ["*", "-opencode.provider.*", "opencode.provider.openai", "-acme.reviewer"]
}

Plugins de terminal (TUI)

Certains plugins ne concernent que l'interface du terminal. Ils se configurent séparément, dans cli.json, et restent actifs même connecté à un serveur distant :

{
  "plugins": ["opencode-acme-cli"]
}

Recharger après un changement

Les fichiers de config surveillés se rechargent tout seuls. Si tu modifies une dépendance locale non surveillée, redémarre le service :

opencode service restart
🔒Un plugin est du code exécuté

Un plugin tourne avec tes droits : il peut lire des fichiers, faire des requêtes réseau, lancer des processus. N'installe que des paquets de confiance, épinglés sur une version précise, et relis un plugin local avant de le charger.

🔧À faire maintenant
  1. Lance opencode plugin list pour voir ce qui est déjà chargé.
  2. Ajoute un plugin avec opencode plugin add <paquet>, puis vérifie-le avec opencode plugin list.
  3. Ouvre le opencode.json modifié et repère l'entrée ajoutée dans plugins.
  4. Retire-le avec opencode plugin remove <paquet>.
✅À retenir
  • Un plugin = du code qui ajoute des capacités (outils, hooks, intégrations).
  • Installation CLI : opencode plugin add / list / update / remove.
  • Découverte auto dans .opencode/plugins/ et ~/.config/opencode/plugins/.
  • - désactive, * vise tout, .* un préfixe.
  • Plugins TUI à part, dans cli.json.

Les commandes : tes raccourcis

Une commande transforme un prompt que tu répètes en un simple /mot. Tu écris la consigne une fois dans un fichier, et tu la déclenches en une frappe. Idéal pour standardiser une façon de travailler.

🎯Objectif

Créer une commande Markdown, utiliser les arguments ($ARGUMENTS, $1…), insérer la sortie d'une commande shell, et choisir l'agent ou le modèle.

La commande la plus simple

Un fichier Markdown dans .opencode/commands/ devient une commande portant le nom du fichier.

Review $ARGUMENTS for bugs and missing tests.

Tu tapes :

/review src/auth.ts

OpenCode envoie au modèle : « Review src/auth.ts for bugs and missing tests. » Le texte que tu tapes après la commande remplace $ARGUMENTS.

⌨️Un modèle de lettre

Une commande, c'est un modèle avec des trous. Tu remplis les trous ($ARGUMENTS, $1, $2) et le courrier est prêt. Au lieu de réécrire toute la demande, tu ne fournis que la partie variable.

Où ranger ses commandes

~/.config/opencode/commands/review.md   ← globale (tous tes projets)
.opencode/commands/review.md            ← projet (prioritaire)

Un sous-dossier devient un préfixe séparé par / : .opencode/commands/team/review.md s'appelle /team/review. Un fichier de projet remplace une commande globale du même nom.

Les arguments : $ARGUMENTS, $1, $2…

Check $1. Focus on $2.

Pour /check src/auth.ts "error handling" : $1 vaut src/auth.ts et $2 vaut error handling. Les guillemets regroupent plusieurs mots. Le plus grand numéro utilisé avale le reste de la ligne.

💡Sans placeholder, le texte est ajouté à la fin

Si le modèle n'a ni $ARGUMENTS ni $1, OpenCode colle simplement ce que tu tapes après la commande, à la suite du prompt.

Insérer une commande shell

Un bloc entre ! et backticks exécute une commande et injecte sa sortie avant l'envoi :

Review this diff:

!`git diff --stat && git diff`

Les placeholders sont remplacés d'abord : dans git log --oneline -$1, un /history 5 donne bien git log --oneline -5.

🔒Bloc shell = exécution immédiate

Un bloc !… s'exécute quand OpenCode évalue la commande, en dehors du système de permissions des outils. N'utilise que des commandes de sources fiables et ne place jamais un argument non vérifié dans un bloc shell.

Choisir l'agent, le modèle, l'exécution

Le frontmatter permet de piloter comment la commande s'exécute :

---
description: Concevoir une solution
agent: plan
model: openai/gpt-5#high
subagent: true
---

Design $ARGUMENTS.
ChampEffet
descriptionTexte affiché dans la liste des commandes.
agentAgent utilisé quand la commande s'exécute.
modelModèle forcé, au format provider/model (et #variant).
subagenttrue : exécution en session enfant (en arrière-plan).

Ordre de priorité du modèle : le model de la commande gagne ; sinon celui de l'agent ; sinon le modèle de la session courante.

La forme JSON

Une commande peut aussi se définir dans la configuration, sous commands (le template est alors obligatoire) :

{
  "commands": {
    "audit": {
      "template": "Audit $ARGUMENTS.",
      "agent": "general",
      "subagent": true
    }
  }
}
🔧À faire maintenant
  1. Crée .opencode/commands/explique.md contenant : Explique ce code simplement : $ARGUMENTS.
  2. Utilise-la : /explique src/app.js.
  3. Crée une deuxième commande resume-diff.md avec un bloc shell !`git diff --stat`.
  4. Ajoute agent: plan au frontmatter et observe le changement de comportement.
✅À retenir
  • Une commande = un fichier .md dans .opencode/commands/ ou ~/.config/opencode/commands/.
  • On déclenche avec /nom ; le sous-dossier devient un préfixe.
  • Arguments : $ARGUMENTS (tout), $1, $2… (positionnels).
  • Bloc !`cmd` : injecte une sortie shell (attention, exécution immédiate).
  • Frontmatter : agent, model, subagent.
Module 5 · Étendre OpenCode

Les serveurs MCP : connecter le monde

MCP (Model Context Protocol) est un standard qui permet à OpenCode de parler à des services externes : une base de données, une API, un CRM, la documentation d'une librairie. C'est la pièce qui transforme l'assistant en outil branché sur ton système d'information.

🎯Objectif

Comprendre ce qu'est un serveur MCP, ajouter un serveur distant ou local, gérer l'authentification, et savoir où mettre un serveur. En clair : MCP = prise universelle entre l'IA et tes outils.

🔌La prise USB-C universelle

Avant l'USB-C, chaque appareil avait son connecteur. MCP joue ce rôle pour l'IA : un seul standard, et n'importe quel outil qui parle MCP peut être branché à l'assistant. Un serveur MCP expose des outils, des ressources et des invites que l'agent peut utiliser.

Distant ou local ?

TypeComment ça marcheExemple
Distant (remote)Un service joignable par URL (HTTP Streamable), souvent avec OAuthContext7 (doc à jour), Sentry
Local (local)Un programme qu'OpenCode lance sur ta machine, via stdioUn serveur de fichiers, un connecteur maison

Ajouter un serveur avec la CLI

Le plus simple : la commande mcp add. Elle écrit le serveur dans la config du projet courant ; ajoute --global pour qu'il soit disponible partout.

# Serveur distant (Context7 : documentation technique à jour)
opencode mcp add context7 --url https://mcp.context7.com/mcp

# Le rendre global (tous les projets)
opencode mcp add context7 --global --url https://mcp.context7.com/mcp

# Serveur local : une commande après --
opencode mcp add everything -- npx -y @modelcontextprotocol/server-everything

# Vérifier l'état des connexions
opencode mcp list

Un serveur connecté apparaît en vert : ✓ context7  connected.

Authentification (OAuth)

Les serveurs distants utilisent OAuth par défaut. Si la liste affiche needs authentication :

  1. Dans OpenCode, tape /mcps pour ouvrir la liste des serveurs.
  2. Sélectionne le serveur : le navigateur s'ouvre pour te connecter.
  3. Reviens dans OpenCode : le serveur passe à connected.
opencode mcp auth sentry    # lancer l'autorisation en CLI
opencode mcp logout sentry  # oublier les identifiants et changer de compte

La configuration à la main

Pour les options fine (en-têtes, secrets, dossier de travail), on écrit sous mcp.servers. Les noms de serveurs ne se placent jamais directement sous mcp en V2 :

{
  "$schema": "https://opencode.ai/config.json",
  "mcp": {
    "servers": {
      "context7": {
        "type": "remote",
        "url": "https://mcp.context7.com/mcp",
        "headers": { "CONTEXT7_API_KEY": "{env:CONTEXT7_API_KEY}" }
      },
      "everything": {
        "type": "local",
        "command": ["npx", "-y", "@modelcontextprotocol/server-everything"],
        "cwd": ".",
        "environment": { "LOG_LEVEL": "info" }
      }
    }
  }
}
💡Jamais de secret en clair

Utilise la substitution {env:NAME} pour les clés. Les expressions shell ($NAME) ne sont pas évaluées dans les chaînes JSON. Pour garder un serveur configuré mais non connecté : mets "disabled": true (il n'y a pas de champ enabled).

Comment les outils s'appellent

Un outil exposé par un serveur est nommé <serveur>_<outil>. Les caractères non alphanumériques deviennent des _ :

serveur : context7
outil   : resolve.library/id
nom     : context7_resolve_library_id

Les invites MCP deviennent des commandes : /context7:find_docs. Choisis donc des noms de serveurs courts et uniques.

Limiter et couper un serveur

On peut masquer ou bloquer des outils sans déconnecter le serveur, grâce aux permissions sur le nom normalisé :

{
  "permissions": [
    { "action": "context7_*", "resource": "*", "effect": "deny" }
  ]
}

Pour retirer un serveur, supprime son entrée de la config où tu l'avais ajouté.

Brancher un outil métier (ex. un CRM)

Le vrai intérêt en entreprise : exposer tes données. Une équipe écrit un petit serveur MCP qui interroge le CRM (lire un client, lister les tickets) et l'ajoute à la config :

{
  "mcp": {
    "servers": {
      "crm": {
        "type": "local",
        "command": ["node", "tools/crm-mcp.js"],
        "environment": { "CRM_TOKEN": "{env:CRM_TOKEN}" }
      }
    }
  }
}

L'agent peut alors répondre à « résume les tickets ouverts du client 42 » en appelant vraiment le CRM — pas en inventant.

🔒Le coût caché : le contexte

Chaque outil MCP consomme du contexte (donc des tokens, donc de l'argent). Ajoute uniquement les serveurs nécessaires, et désactive ceux que tu n'utilises pas. Un outil qui expose 50 fonctions gonfle chaque requête.

🔧À faire maintenant
  1. Ajoute le serveur Context7 : opencode mcp add context7 --url https://mcp.context7.com/mcp.
  2. Lance opencode mcp list et vérifie l'état de la connexion.
  3. Dans OpenCode, tape /mcps et connecte-toi si demandé.
  4. Demande à l'agent d'utiliser la documentation d'une librairie via Context7, et observe l'appel d'outil.
✅À retenir
  • MCP = standard pour brancher des outils externes à l'agent.
  • Deux types : remote (URL) et local (commande stdio).
  • CLI : opencode mcp add / list / auth / logout ; dans l'interface : /mcps.
  • Config sous mcp.servers (jamais directement sous mcp).
  • Noms d'outils normalisés <serveur>_<outil> ; permissions pour bloquer.
Module 6 · Pratique & méthode

Bien prompter & le fichier AGENTS.md

Un bon agent avec un mauvais prompt donne de mauvais résultats. La compétence la plus rentable n'est pas technique : c'est de savoir demander. Et il existe un fichier magique qui évite de tout répéter : AGENTS.md.

🎯Objectif

Apprendre une méthode de prompt simple et fiable, puis automatiser le contexte du projet avec AGENTS.md et la commande /init.

La recette d'un bon prompt

Un prompt efficace contient, dans cet ordre :

  1. Le contexte. De quoi parle-t-on ? (fichier, techno, contrainte).
  2. L'objectif. Que veut-on obtenir ? Un résultat observable.
  3. Les contraintes. Ce qu'on interdit ou impose (pas de nouvelle dépendance, garder le style…).
  4. Le format attendu. Un diff, un plan, une liste de fichiers.
  5. La demande de plan. « Propose d'abord, exécute ensuite. »
Mauvais : "corrige le bug" Bon : Contexte : le panier se vide après un rafraîchissement. Objectif : le panier doit survivre au rechargement. Contrainte: pas de nouvelle dépendance. Format : montre-moi le plan AVANT de modifier.
👨‍🎓La commande à un stagiaire

« Fais le rapport » donne un mauvais rapport. « Fais un rapport de 2 pages sur les ventes du trimestre, en comparant à l'an dernier, avec un tableau, avant vendredi » donne ce que tu veux. L'IA fonctionne pareil : plus tu précises, moins tu itères.

Les 5 réflexes qui changent tout

RéflexePourquoi
Plan avant actionL'agent plan explore sans rien casser ; tu valides, puis tu exécutes.
Une tâche à la foisUn prompt = un objectif. Les demandes empilées se noient.
Donner un exempleMontrer le résultat attendu vaut mille explications.
Demander la justification« Explique tes choix » révèle les erreurs de raisonnement.
Corriger, pas repartirPrécise ce qui ne va pas : l'agent garde le contexte utile.

AGENTS.md : le contexte permanent

Répéter les conventions du projet à chaque conversation est fatigant. AGENTS.md est un fichier à la racine du projet qu'OpenCode lit automatiquement. Il décrit ton contexte une fois pour toutes.

/init

La commande /init analyse le projet et génère un AGENTS.md de départ. On le complète ensuite à la main :

# Projet : Boutique (React + Vite)

## Commandes
- Démarrer : npm run dev
- Tester : npm test
- Lint : npm run lint

## Conventions
- JavaScript, pas de TypeScript.
- Composants dans src/components/.
- Pas de nouvelle dépendance sans justification.

## À ne jamais faire
- Modifier package-lock.json à la main.
- Commit sur main sans passer par une branche.
💡Place-le au bon endroit

Un AGENTS.md à la racine décrit tout le projet. Tu peux aussi en mettre dans un sous-dossier pour préciser des règles locales. Plus il est précis et court, mieux il est suivi : des règles concrètes valent mieux qu'un long roman.

🔧À faire maintenant
  1. Ouvre un de tes projets dans OpenCode et lance /init.
  2. Relis l'AGENTS.md généré : corrige les erreurs, ajoute tes commandes réelles.
  3. Relance une tâche : l'agent doit suivre tes conventions sans que tu les répètes.
  4. Réécris un prompt brouillon en suivant les 5 éléments (contexte, objectif, contraintes, format, plan).
✅À retenir
  • Un bon prompt = contexte + objectif + contraintes + format + demande de plan.
  • Planifier avant d'agir économise du temps et des tokens.
  • AGENTS.md porte le contexte du projet ; /init le génère.
  • Court et concret : des règles précises sont mieux suivies.

Mini-projet : ton assistant de A à Z

Place à la pratique. On construit, étape par étape, un assistant de projet complet : contexte, agent de revue, skill, commande et serveur MCP. Chaque étape réutilise ce que tu as appris — rien de nouveau.

🎯Objectif

Assembler toutes les briques du cours dans un seul projet réel et vérifier que l'ensemble fonctionne ensemble.

💡Comment suivre ce mini-projet

Prends n'importe quel petit projet à toi (ou crée un dossier demo-assistant/ vide). Fais les 6 étapes dans l'ordre. À la fin, tu auras une configuration réutilisable pour tous tes projets.

Ce qu'on va construire

demo-assistant/ ├── AGENTS.md (étape 1 : le contexte) ├── .opencode/ │ ├── agents/ │ │ └── reviewer.md (étape 2 : un agent de revue) │ ├── skills/ │ │ └── conventions/SKILL.md (étape 3 : une skill) │ └── commands/ │ └── verifier.md (étape 4 : une commande) └── opencode.json (étape 5 : un serveur MCP)

Étape 1 — Le contexte du projet

On commence par donner à l'agent le minimum vital : comment lancer et tester le projet, quelles sont les conventions.

# Projet : démo assistant

## Commandes
- Lancer : npm run dev
- Tester : npm test

## Conventions
- JavaScript uniquement.
- Chaque fonction exportée a un commentaire d'une ligne.

## Interdits
- Pas de nouvelle dépendance sans validation.

Vérifie : lance OpenCode dans ce dossier et demande « quelles sont les conventions de ce projet ? ». L'agent doit répondre sans que tu les répètes.

Étape 2 — Un agent de revue

On crée un subagent qui relit le code sans jamais l'éditer. C'est le patron du moindre privilège : il lit, il commente, il ne modifie rien.

---
description: Relit le code selon les conventions du projet
mode: subagent
permissions:
  - action: edit
    resource: "*"
    effect: deny
---

Tu es un relecteur exigeant.
Tu t'appuies sur AGENTS.md.
Tu signales : bugs, tests manquants, écarts aux conventions.
Tu ne modifies jamais les fichiers : tu proposes.

Vérifie : demande à l'agent build d'utiliser ce subagent de revue sur un fichier.

Étape 3 — Une skill réutilisable

On range la méthode de revue dans une skill, pour la réutiliser dans n'importe quel projet.

---
name: Conventions
description: Vérifier le respect des conventions du projet
---

## Marche à suivre
1. Lis AGENTS.md.
2. Liste les écarts aux conventions, du plus grave au moins grave.
3. Pour chaque écart, propose une correction sans l'appliquer.

Vérifie : la skill doit apparaître quand le sujet est la relecture ou les conventions.

Étape 4 — Une commande

On emballe le tout dans une commande unique, déclenchée en une frappe.

---
description: Vérifier les fichiers modifiés
agent: general
---

Vérifie $ARGUMENTS :
1. Respecte-t-il les conventions d'AGENTS.md ?
2. Y a-t-il des tests manquants ?
Rends une liste courte, classée par gravité. Ne modifie rien.

Vérifie : dans OpenCode, tape /verifier src/app.js.

Étape 5 — Un serveur MCP

On branche un outil externe pour que l'agent ait de la documentation toujours à jour.

opencode mcp add context7 --url https://mcp.context7.com/mcp
opencode mcp list

Vérifie : /mcps montre le serveur connected, et l'agent l'utilise quand tu demandes la doc d'une librairie.

Étape 6 — Le test final

Tout est en place. Voici une mission complète qui utilise chaque brique :

/plan Ajoute une page "Contact" à l'application.
Format : d'abord un plan, ensuite une estimation
des fichiers touchés. Ne code rien pour l'instant.

Puis :

  1. Valide le plan, passe en /build et fais exécuter.
  2. Lance /verifier sur les fichiers modifiés.
  3. Demande la doc de la librairie utilisée (le serveur MCP doit répondre).
🔧À faire maintenant
  1. Réalise les 6 étapes ci-dessus dans un projet.
  2. Copie le dossier .opencode/ obtenu dans un second projet et constate qu'il fonctionne tel quel.
  3. Crée un commit Git pour versionner ta configuration d'assistant.
✅À retenir
  • AGENTS.md = contexte ; l'agent le lit tout seul.
  • Le subagent de revue illustre le moindre privilège (lecture seule).
  • Skill = méthode réutilisable ; commande = raccourci ; MCP = outil externe.
  • Une config d'assistant se versionne et se partage avec l'équipe.
